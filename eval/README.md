# Evaluation files

All inputs follow the same convention as the App tab: text, or the path of a file under `eval/inputs/` (an image, a document…), written from the repo root, e.g. `eval/inputs/parcel_07.jpg`.

## `cases.csv`: the end-to-end test set

30 or more cases written by the team, from realistic inputs, not generated by the model you are testing.

| Column | Content |
|---|---|
| `id` | Short unique id, e.g. `c01` |
| `input` | The input (see above) |
| `kind` | `normal`, `hard` (should work but is difficult), `review` (should be sent to a person) or `out_of_scope` (the product should refuse or say it cannot help) |
| `expected` | What a correct output is: a label, a value, or a short description the judge can check against |
| `baseline` | What happens to this case today, without the product |
| `notes` | Optional: why the case is in the set |

Include at least 5 `hard`, 5 `review` and 3 `out_of_scope` cases, and some `normal` ones: the drift demo uses them as normal traffic.

## `human_labels.csv`

If you use an LLM judge: your own labels for 20+ cases (`id`, `label`, `comment`). Compute your agreement with the judge in code.

## `reference.csv`: what normal inputs look like

30 or more normal inputs (one `input` column), **not** the ones in `cases.csv`: for example, a sample of the data your components were built or tested on. `uv run python main.py reference` turns them into `monitoring/reference_features.csv`, which the Monitoring tab and the drift demo compare live inputs against. Commit both.

## `shifted.csv`: the drift demo

10 or more inputs that you shifted on purpose (one `input` column): darker photos, another language, another customer segment… `uv run python main.py drift-demo` checks that your alert fires on these and stays quiet on the `normal` cases.
