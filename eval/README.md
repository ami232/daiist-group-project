# Evaluation cases

`cases.csv` holds your end-to-end test set: 30 or more cases written by the team, from realistic inputs, not generated by the model you are testing.

| Column | Content |
|---|---|
| `id` | Short unique id, e.g. `c01` |
| `input` | The input as text, or the path of a file under `eval/inputs/` (an image, a document, a CSV row) |
| `kind` | `normal`, `hard` (should work but is difficult), `review` (should be sent to a person) or `out_of_scope` (the product should refuse or say it cannot help) |
| `expected` | What a correct output is: a label, a value, or a short description the judge can check against |
| `baseline` | What happens to this case today, without the product |
| `notes` | Optional: why the case is in the set |

Include at least 5 `hard`, 5 `review` and 3 `out_of_scope` cases. If you use an LLM judge, put your own labels for 20+ cases in `human_labels.csv` (`id`, `label`, `comment`) and compute your agreement with the judge in code.

Shifted inputs for the drift demo go in `eval/shifted/`, and the reference set the drift check compares against goes wherever your monitoring code reads it (say where in REPORT.md).
